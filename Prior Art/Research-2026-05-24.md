# Prior Art — What Already Exists (2026-05-24)

> Landscape research before committing to build. Goal: know who has already tried each piece of FinAgent, what they learned, what to steal, what to avoid. Companion to [Infrastructure.md](../Infrastructure.md), [Agent Framework PydanticAI](../Tech%20Decisions/Agent%20Framework%20PydanticAI.md), [Research Notes 2026-05-18](../Models/Research/Research%20Notes%202026-05-18.md).

---

## Headline findings

1. **No single project today combines all five FinAgent pillars** — (a) local-only Ollama inference, (b) PydanticAI-grade structured tool use, (c) personal-ledger CRUD, (d) Signal as primary interface, (e) layered memory. Every project covers 1–3 of these; nobody covers all five. Your stack picks an empty quadrant.
2. **Two architectural patterns have already won** for "LLM + personal finance":
   - **The MCP bridge pattern** — wrap an existing ledger app (Actual, YNAB, hledger) in an MCP server, point Claude/GPT at it. ~10+ implementations exist. Low effort, but the LLM is *not* yours and your data leaves the box.
   - **The function-call wrapper pattern** — embed AI inside the finance app (Maybe Finance, Copilot Money, Cleo). Tighter UX but the AI is bolted on after-the-fact, not native.
   FinAgent is neither. It's **agent-native** (the assistant *is* the app, the ledger is its memory). That's the actually-novel position.
3. **The hard lesson from every prior project: LLMs hallucinate at the worst possible moment — money math.** Beancount.io documented this most clearly. Off-the-shelf LLMs *"don't have inherent precision with numbers"* and silently miscalculate balances even when confident. The mitigations every successful project uses: (a) deterministic arithmetic in tools, never in the prompt, (b) double-entry validation as a hard gate, (c) "trust but verify" review steps before persisting.
4. **Categorization is the one task LLMs unambiguously beat rules at** — but only as a *fallback after deterministic rules*. Beanborg's hybrid (rules → ML → LLM) is the consensus design. Copilot Money claims ~93% first-pass accuracy with a per-user model.
5. **Your 4 GB VRAM constraint is harsher than the prior-art literature assumes.** Every "small model for tool calling" guide bottoms out at **Qwen 2.5 7B at 5–6 GB Q4**. Sub-5GB tool-calling is essentially unexplored territory in published benchmarks — which matches what you found in [Research Notes 2026-05-18](../Models/Research/Research%20Notes%202026-05-18.md) Headline #2.

## Tier 1 — Direct competitors (closest in shape to FinAgent)

### Maybe Finance — `maybe-finance/maybe`

The closest big-name reference. Rails + React app, open-sourced Jan 2024, now widely self-hosted (Umbrel app store entry exists). AI is **opt-in**, **off by default**, **function-calling against the user's own data**.

- **AI architecture (per their wiki):** when the user asks "what is my current net worth?", the LLM issues a function call back to the Maybe app; the app returns the data; the LLM composes the reply. **PII is explicitly stripped** before leaving the box: names, emails, account numbers never reach the AI provider. They send "the least amount of data required."
- **Provider model:** assumes OpenAI by default. Self-hosters can disable AI entirely; cloud/managed version stores chat history server-side.
- **Stack:** Rails + Sidekiq + Redis + Postgres, single-container Docker deployable.
- **What to steal:** the PII-stripping contract is a clean idea even when your provider is local. Strip names/account-numbers in the tool-result layer regardless — defense in depth if you ever switch to a cloud provider for diagnostics.
- **What's different about FinAgent:** Maybe is a finance app with AI on top. FinAgent is an agent with finance tools. Maybe's chat is a sidebar; yours is the front door (Signal).

### Personal Financial AI Agent — `merendamattia/personal-financial-ai-agent`

The closest individual-developer project. **Streamlit + multi-LLM (Ollama / Gemini / OpenAI) + portfolio-recommendation RAG over 10y ETF history.**

- **Ollama default model:** `qwen3:0.6b` — interesting choice, very small. Suggests they prioritise running-anywhere over reasoning quality.
- **Pattern:** profile-extraction-via-conversation → RAG against ETF dataset → recommendation. Not transactional/ledger-style; **planning-oriented**.
- **What to steal:** the multi-LLM abstraction with environment-based provider switching. You'll want this for development (local Ollama) vs. eval (cloud frontier model as ground-truth oracle).
- **What's missing:** no transaction CRUD, no memory layer beyond JSON profile, no messaging interface. Pure desktop/web Streamlit.

### Personal Finance Agent — `Kirushikesh/Personal-Finance-Agent`

The literal name-match. **Autogen + GPT-4 + SQLite.** Two agents: Storage Assistant (accepts transactions in dialogue) and Analysis Assistant (NL → SQL).

- **Stack:** Autogen (not PydanticAI), GPT-4 (not local), CLI only. ~11 commits, looks abandoned.
- **Data model:** date, category, amount, description, type — minimal. No multi-account, no double-entry.
- **What to learn:** the *idea* of split agents (one for write, one for read) is interesting and maps onto a procedural-memory split. But NL→SQL is a known foot-gun for hallucination on financial data; you want a tool surface, not raw SQL.

### Finance Analyzer Using Local LLMs — `spacedust10/finance-analyser-using-local-LLMS`

**Streamlit + Llama 3.1 via Ollama + Plotly.** CSV-in, dashboard-out. No transaction CRUD, no agent, no memory — read-only analysis.

- Notable because it's one of the few **end-to-end local** projects. Worth glancing at for the chart layout.

### yorkeccak/finance — "world's most powerful open-source financial AI assistant"

Markets itself as institutional-grade but is structured as a **Vercel AI SDK + Ollama + Daytona sandbox** stack. Function-calling with streaming. Auto-detects local providers (Ollama, LM Studio) and falls back to OpenAI.

- **Investment-focused, not personal-budget-focused** — SEC filings, Monte Carlo on stock prices.
- **What to steal:** the **Daytona sandbox for code execution** pattern. If you ever want the agent to run pandas on your ledger, sandboxed Python execution is the right shape (vs. trying to make the LLM compute directly).

## Tier 2 — Adjacent pieces (one slice of the FinAgent stack)

### Plain-text accounting + LLM ecosystem

This community has been at LLM-assisted bookkeeping longer than anyone. Their lessons transfer almost completely.

- **Beanborg** (`luciano-fiandesio/beanborg`) — **the consensus design for hybrid categorization:**
  1. Rule-based matching (lookup files for payees, accounts) — deterministic, **always wins**
  2. ML model gives top-3 predictions if no rule matches
  3. **Optional ChatGPT** appears as a 4th option *only if user opts in*
  Rules are paramount. LLM is the last fallback. This is the right ordering for FinAgent's categorization tool.
- **beancount.io blog** (their LLM articles, July 2025) — best summary of what works and what fails in LLM-assisted bookkeeping:
  - **Works:** categorization, anomaly detection ("this fuel charge is 10× your usual"), partial-entry completion, onboarding tutor.
  - **Fails:** double-entry syntax without explicit account list in prompt, precise arithmetic, account-name hallucination.
  - **Standard mitigations:** include valid chart of accounts in every prompt, few-shot examples, post-validation with `bean-check`, batch processing for consistency, human review of all unstructured input.
- **Real-user friction quote:** *"about 4 hours catching up on importing the past ~8 months"* — even with AI, the **ingestion bottleneck dominates**, not the categorization step. Build for ingestion first.
- **Beanquery AI** (Beancount discussion #971) — proposed but not yet built; NL → Beancount-query translation. Direct evidence that the community wants what FinAgent's "read" tools provide.
- **hledger-mcp / ledger-cli MCP servers** — wrap CLI in MCP, agents call CLI commands, parse stdout. **The journal file never leaves the local box.** This is a viable architecture for FinAgent's storage layer if you ever decide Postgres is over-engineered for personal scale.

### MCP-bridge ecosystem (the lowest-effort prior art)

These projects each wrap an existing finance app in MCP. They're not direct competitors — they're a **catalog of tool surfaces** to copy.

- **Actual Budget MCP** (`s-stefanov/actual-mcp`) — **the most complete tool surface** in the wild:
  - **Read:** `get-transactions` (filter by account/date/amount/category/payee), `get-accounts`, `balance-history`, `spending-by-category`, `monthly-summary`, `get-grouped-categories`, `get-payees`, `get-rules`
  - **Write:** `create-transaction`, `update-transaction`, full CRUD on categories/category-groups/payees/rules
  - **Built-in prompts:** `financial-insights`, `budget-review` — pre-canned analyses
  - This is *the* reference list. If FinAgent's tool surface differs from this, that difference should be a deliberate choice.
- **YNAB MCP** (`cinnes/ynab-mcp`) — 16+ tools. Same shape. Notable: tokens stored in **OS keyring** (Windows Credential Manager / macOS Keychain). Steal this pattern for any API key you don't want in `.env`.
- **Firefly III MCP server** — claims 100% API coverage, AI-agnostic.
- **Mem0 MCP** — exposes Mem0's memory store as MCP tools.

**Pattern across all four:** read tools heavily outnumber write tools (~3:1), each tool returns structured JSON, all auth happens server-side, no LLM-specific code anywhere.

### Categorization-only tools

- **`sakowicz/actual-ai`** — Actual Budget AI categorizer. Multi-provider (OpenAI/Anthropic/Google/Ollama/OpenRouter/Groq), default Ollama model `phi3.5`. **Configurable prompt via Handlebars** in env var. Cron-driven batch. Marks unclassifiable as "not guessed" to avoid reprocessing — a simple form of negative-cache. Optional ValueSerp/DuckDuckGo web search for unknown merchants. **Failure-state design worth copying.**
- **`aelzeiny/YNAB_GPT`** — auto-categorizes YNAB transactions, flags categorized ones with blue flag for review. **Trust-but-verify made visible in the UI.**

### Bank statement ingestion (the un-glamorous half of the problem)

- **`sebastienrousseau/bankstatementparser`** — **best-in-class architecture**. Tiered:
  1. **Deterministic parsers first** (CAMT.053, PAIN.001, CSV, OFX, QFX, MT940) — $0, fastest.
  2. **Text-LLM via Ollama** for digital PDFs (configurable backend).
  3. **Vision-LLM** for scanned PDFs, opt-in.
  - Every row carries a `transaction_hash` (MD5), a `source_method` tag, and (for LLM rows) a `confidence` score. **Provenance is first-class.**
  - **"Golden Rule" balance check:** `opening + credits − debits == closing` → `VERIFIED | DISCREPANCY | FAILED`. A non-negotiable invariant that catches LLM extraction errors.
  - **PII redaction on by default** in console output; opt-in to disable. Defense-in-depth even on local-only stacks.
  - This is the import-pipeline shape FinAgent should adopt almost verbatim. Indian bank PDFs are the chaos case — the tiered LLM-fallback design is exactly what handles that variance.

### Signal-bot + local LLM ecosystem

The Signal-bridge prior art is **smaller than the MCP ecosystem but architecturally more direct**.

- **`maciejjedrzejczyk/uoltz`** — *the* reference design. Architecture: `Signal ↔ signal-cli-rest-api (Docker) ↔ Python bot ↔ Strands agent ↔ local LLM`.
  - Pluggable skill modules (`brainstorm`, `research`, `summarize`, `web_search`, `notes`, `shell`, `skill_builder`).
  - **YAML-defined scheduled jobs in `schedules/` with cron expressions** — sends proactive messages without user prompt. This is the "morning briefing" pattern FinAgent needs.
  - **Voice messages transcribed locally with faster-whisper** before reaching the agent. If you want voice-note expense logging ("just paid 600 for groceries"), this is the path.
  - One example finance skill ships (`amzn_stock.yaml`) — periodic stock-price check. Nothing transactional.
  - **Verdict:** uoltz is the closest thing to FinAgent's Signal interface architecture. Steal the skill-registry + scheduler + Docker layout.
- **`aljazceru/signallama`** — simpler bridge, LiteLLM-mediated provider abstraction. Useful if you want multi-provider chat without skills/scheduling.
- **`kasp0r/ollama-signal-bot`** — single-purpose. **In-memory** conversation history (lost on restart), phone-number allowlist, slash commands (`/model`, `/reset`, `/verbose` for token telemetry). Polling loop, **no async story for long inference** — a documented blind spot. Treat this as "what not to do for persistence" but the **`/verbose` token-telemetry slash command is a great idea to steal**.

### PydanticAI specifically

- **Official `bank_support` example** — the closest official endorsement of finance-shaped agents. `SupportOutput` model with `support_advice`, `block_card`, `risk` (0–10). Pattern: agent + dependency-injected DB + one tool (`customer_balance`) + structured output. **This is the template to start from** — your `LogExpense`, `QueryLedger`, `Categorize` agents are siblings of this example.
- **`abdallah-ali-abdallah/pydantic-ai-agents-tutorial`** — 14 progressive examples, all local-model-first. Author's tool-calling model recommendations (for PydanticAI specifically): **Llama 3.1 8B Instruct** and **Qwen 2.5 14B/32B**. Both are above your VRAM budget. Implies your 3B–4B class is **off the PydanticAI happy path** — expect more retry/repair behavior than the tutorial suggests.
- **`rjaskonis/pydantic-ai-mem0`** — concrete PydanticAI + Mem0 + Postgres-pgvector wiring. **Same stack as yours.** Architecture: `main.py` (agent loop), `mem0_settings.py` (memory config), `async_mem0.py` (non-blocking wrapper), `pyproject.toml`. Tools: `get_current_date`, `get_user_relevant_memories`. **Read this repo before writing your memory layer.**
- **Mem0 paper's ADD/UPDATE/DELETE/NOOP decision** (already in [Memory Research-23-05-26](../Memory/Research-23-05-26.md)) — this is *the* memory write-path. Reaffirmed across prior art.

### General local-LLM personal-assistant frameworks

- **OpenClaw** — 24+ messaging channels (incl. Signal), Ollama-native, plugin marketplace (ClawdHub). Could in principle host a "finance skill" instead of building from scratch. **Risk:** you become a tenant of someone else's plugin platform, and the framework decides your agent shape. **Status:** went through a governance transition in early 2026 — stable but worth watching before betting on it.
- **AnythingLLM** — document-RAG focused; not the right shape for transactional finance.
- **Jan.ai** — desktop chat UI only; no agent or skills layer.
- **n8n self-hosted AI starter kit** — workflow-builder, not agent. Worth knowing exists as a "let me automate the import pipeline visually" tool if you ever want it.

### FinRobot / FinGPT / FinRL (research-grade)

**Out of scope for personal finance.** Multi-agent equity-research platforms, OpenAI/cloud-first, focused on stock forecasting and SEC filing analysis. The "Financial Chain-of-Thought" layering they describe is interesting in the abstract but applies to market analysis, not budgeting. **Skip — wrong shape.**

## Critical findings about LLMs in finance (across all prior art)

### Hallucination is structural, not a polish issue

- **arXiv 2511.21756 (Nov 2025) "Dissecting the Ledger: Locating and Suppressing Liar Circuits in Financial LLMs"** — researchers used causal tracing on GPT-2 XL to localize arithmetic hallucination circuits. Concrete example: "Revenue growth from 50M to 30M" → model answers "50%" instead of -40%. **Specific computational pathways are broken.** This is being solved at the architecture level, not the prompt level. Implication: do not put arithmetic in the prompt path. Ever.
- **arXiv 2311.15548 "Deficiency of LLMs in Finance"** — off-the-shelf LLMs hallucinate seriously on financial tasks. Mitigations evaluated: few-shot, DoLa, RAG, prompt-based tool learning. **Tool learning + RAG is the consensus best mitigation.** This validates the PydanticAI tool-first architecture.
- **FAITH benchmark (arXiv 2508.05201)** — specifically measures intrinsic *tabular* hallucinations in finance. Worth running on candidate models if/when you have eval infrastructure.

### Categorization is the easy win

Beancount.io documents real users feeding `"STARBUCKS #12345"` → getting `Expenses:Food:Coffee` reliably. Anomaly detection ("this is 10× your usual fuel") also works well. Both are **classification tasks where the LLM never has to do math.**

### What consistently breaks

- Account-name hallucination → mitigate by **always including the valid chart of accounts in the system prompt**.
- Imbalanced double-entry → mitigate by **post-validation tool** that rejects and asks the model to retry.
- Wrong arithmetic → mitigate by **never letting the model do the arithmetic** — pass amounts as strings, sum in Python.
- Stale context (Maybe Finance specifically called this out) → mitigate by **refreshing context on every state change**, not once-per-session.

### Trust-but-verify is the universal pattern

Every successful prior project has a human-review step before persistence:

- Actual-AI marks transactions with a "guessed" tag for review.
- YNAB_GPT flags categorized transactions with a blue flag.
- Beancount workflow always runs `bean-check` post-hoc.
- Bank statement parser balance-check before commit.

**Implication for FinAgent:** Signal-thread review of LLM-categorized transactions before they hit the ledger. Auto-commit only for high-confidence + rules-matched transactions.

## Mistakes to avoid (also concrete)

- **Do not give the LLM raw SQL access** (Kirushikesh did) — exposes the model to numeric tasks it can't do reliably. Use named tools that return aggregates.
- **Do not let the LLM do arithmetic.** Always pass amounts to a Python function. Even "what's 3 × 250?" goes to a tool.
- **Do not store conversation in process memory only** (ollama-signal-bot did) — restart = lost context. Postgres-persisted from day one.
- **Do not put PII into prompts** even when local. Strip it in the tool layer.
- **Do not assume small models do multi-step tool calling well.** Per InsiderLLM 2026 guide: "smaller models lose coherence after 2–3 steps." Design tools to do more per call rather than chaining many short calls.
- **Do not skip the chart-of-accounts injection.** Every Beancount-LLM project that tried this learned the same lesson.
- **Do not ship without an eval suite.** 2026 consensus: 100–200 hand-labelled cases that mirror your real workload. LLM-as-judge for fast iteration; manual spot-check periodically.

## Gaps in the landscape (where FinAgent can actually be different)

1. **Local-only, agent-native, messaging-first personal finance assistant — no one occupies this quadrant.** Maybe is local-deployable but web-UI-first. uoltz is messaging-native but generic. Actual is local but not agent-native. The intersection is empty.
2. **Privacy-preserving Indian-banking ingestion.** Every bank-statement-parser project is built for Western banks (SEPA, ACH, OFX). Indian PDFs (HDFC, SBI, ICICI statements, UPI exports, GPay/PhonePe history) are an open ingestion problem with no good local-LLM solution shipped today.
3. **Conversational ledger correction.** Every system today is "log first, categorize later." A user-facing "oh, that 4500 wasn't groceries — it was the vet" conversational repair flow is missing across the board.
4. **Memory that meaningfully understands financial patterns.** Mem0 + PydanticAI work mostly with generic memories. A semantic-memory layer that consolidates "user usually eats out on Fridays" or "rent always falls on the 5th" doesn't exist in any prior art reviewed.
5. **Proactive financial reasoning via scheduled briefings.** uoltz has the *machinery*. No finance project uses it. "Your spending is 30% over baseline this week" pushed at 7am Monday is novel as a packaged product.

## Open questions worth deciding before building

- **Q1:** Embed an existing ledger (Actual/hledger/Beancount) and put the agent on top, or build the ledger primitive yourself in your Postgres schema?
  - *Argument for embedding:* Beanborg/Actual-AI did this; smaller surface area; mature ingestion.
  - *Argument for from-scratch:* Indian banking ingestion is the bottleneck and existing ledgers don't help; agent-native means the ledger is *just* a tool-callable table, not a separate product.
- **Q2:** Postgres + pgvector, or SQLite for v1? Mem0 demos use Postgres + pgvector. SQLite is simpler. **The Fortress is a single box** — Postgres is already over-engineered for personal scale unless multi-process concurrency matters.
- **Q3:** Does the agent ever auto-commit, or always require Signal-thread approval? Copilot Money auto-commits with 93% accuracy and a review queue. At your model scale you cannot match 93% on day one. **Start review-only**, relax over time.
- **Q4:** One agent or many? Kirushikesh used two (store/analyze). Uoltz uses one with skills. FinRobot uses N (overkill for personal). PydanticAI bank-support uses one. **Lean: one agent, many tools, until that breaks.**
